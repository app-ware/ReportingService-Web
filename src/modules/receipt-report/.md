# Receipt Report Export — Design (proposal, not yet implemented)

> Mirrors `src/modules/invoice-report` and `src/modules/incident-report` (see their `.md`) — same
> split, same conventions. This file is a **design/contract doc only** — no code has been added to
> this service yet. Written for review/approval before implementation starts on either repo.

## 1. Overview

Renders the **Receipt** PDF for a recorded payment (legacy: `ExportInstallmentReportData`, SPs
`getChildReceipt` / `getChildReceiptExtra`, Crystal Reports `ReceiptReport.rpt` /
`ReceiptReportCustomized.rpt` / `ReceiptReportSmall.rpt`). `PrintableReport_Types.printable_report_
type_id = 2` ("Receipt", already seeded). Same division of labor as the other two reports: **all
data aggregation, currency/amount-in-words/thousands formatting, and image-file resolution happens
in NurseryServices-Web**; this service stays "dumb" — JSON in, PDF out.

Reference legacy source: `ExportInstallmentReportData()` (C# WCF, supplied directly), and a real
production sample PDF (`[Demo] mostafa gg55_dsvdsggsd_receipt.pdf`, supplied directly) used as the
visual ground truth below — same approach as `invoice-report/.md`: no legacy SP bodies were
available, so the field list is reconstructed from the rendered sample cross-checked against the
already-modernized `payment-student-payment` module's schema/SP
(`iCareWebPanel_getPaymentsData_paginated`, `StudentPaymentResponseDto`) rather than the legacy SPs
directly.

**One genuinely new wrinkle vs. the other two reports**: a receipt has **two source rows** (legacy's
`InstallmentType` param, already a first-class concept in `payment-student-payment` — see
`student-payment-logic.md` §1) and an **A4/A5 report-size toggle** neither Invoice nor Incident
Report has (§2 point 5 below).

## 2. Data flow

1. NurseryServices-Web's new `payment/payment-student-payment/export` sub-module resolves **one**
   payment row, identified by `(installmentId, installmentType)` — same two params legacy's
   `InstallmentID`/`InstallmentType` take (no new stored procedure — a single-record read, same
   reasoning as invoice-report-export/incident-report-export, skill 12 §2):
   - **`installmentType = 1`** (invoice installment — the sample's source): `Child_Payments` row
     (`installment_id` has a **unique index** in the modern schema — confirmed one payment row per
     installment, no partial-payment fan-out to worry about) → joined to `Fees_Installments` →
     `Child_Invoice` (for `center_invoice_number`, `invoice_title`) — `invoice_title` is what the
     sample's single "Description" table row shows (`"dsvdsggsd"` matches `Invoice: dsvdsggsd`
     exactly), **not** a `Child_Fee` breakdown the way the Invoice PDF shows one row per fee — a
     receipt is one payment against one installment, so one description line, not a fee table.
   - **`installmentType = 2`** (extra payment): `Child_Extra_Payment` row (payment fields live
     directly on it — no separate payment table) → joined to `Center_Extra_Payments` for
     `extra_payment_title` (the presumed `Description` equivalent for this branch — **not**
     confirmed against a type-2 sample, flagged in §6).
   - Student/parent names via `vwChildClassParent`, same as the other two reports.
   - `Care_Center` (name/address/landline/logo) + `center_currency` → `Currency.currency_name`, same
     reads invoice-report-export already added.
   - `Payment_Type` lookup for the payment method label (`"Cash"` in the sample —
     `payment_type_title`).
   - `Center_Printable_Report_Settings` for `printable_report_type = 2` ("Receipt").
2. **Report size (A4/A5) — new for this report**: legacy reads
   `Center_PrintableReport_Sizes(center_id, report_type=2)` (falling back to the `center_id = -1`
   global default row, `ORDER BY center_id DESC` picks the center-specific row when one exists — same
   cascade shape as skill 13 §1b's Excel export style settings) to choose between
   `ReceiptReport.rpt` / `ReceiptReportCustomized.rpt` (A4) and `ReceiptReportSmall.rpt` (A5,
   **always** small layout, header/footer customization is skipped entirely for A5 regardless of
   `use_images` — legacy's `Report_Customization_Variants` table is only built when `use_images ==
   true AND reportSize == A4`). The modern equivalent objects already exist and are already
   read/written elsewhere in this codebase: `Center_PrintableReport_Sizes` /
   `PrintableReport_Sizes` entities, `NotificationSettingsService.getReportSizes()` /
   `.updateReportSize()` (`center-settings/notification-settings`). The export service reads the
   effective size the same way that service does (center-specific row, else the `-1` global
   default) rather than re-deriving the cascade.
3. **Computed in NurseryServices-Web** (skill 12 §7):
   - `amount` formatted **with a thousands separator** (`"1,254.00"` in the sample) — unlike
     Invoice's plain `toFixed(2)` (`"328.00"`, never confirmed either way since 328 has no thousands
     separator to show regardless). Flagged in §6 as worth revisiting on the already-shipped invoice
     export for consistency, not silently changed here.
   - `amountInWords` — same in-house helper `PaymentTuitionExportService` already built for the
     Invoice export (`numberToWords`/`buildAmountInWords`), reused as-is (no second implementation).
   - `date` — presumed `Child_Payments.payment_date` / `Child_Extra_Payment.payment_date` (the
     receipt's issue date, distinct from `payment_value_date`), formatted `dd/MM/yyyy` (`"15/06/2026"`
     in the sample) — **note this is the opposite day/month order from Invoice's `issueDate`
     (`MM/dd/yyyy`)**. Not reconciled into one shared convention — each report matches its own
     legacy sample exactly, same "sample wins" principle as skill 13 §6b, even when two reports
     disagree with each other.
4. Images resolved to Base64 server-side, nullable, soft-fail-to-null — identical helper shape to
   the other two exports, against `printable_report_type = 2`, and only attempted at all when the
   effective report size is A4 (§2 point 2).
5. NurseryServices-Web `POST`s the assembled `ReceiptReportTemplateData` JSON to this service.
6. This service compiles `receipt-report.hbs`, renders it via Playwright, returns the PDF buffer —
   own `ReceiptReportPdfService`, same one-class-per-report-module convention as the other two.
7. NurseryServices-Web streams the PDF back via the same ticket/download-URL pattern, in a new
   `payment-student-payment/export/` sub-module, filename `"{studentName}_{description}_
   receipt.pdf"` (matches the legacy filename convention exactly — underscore-joined, unlike
   Invoice's space-joined `"{studentName} {invoiceTitle} Invoice.pdf"` — again, sample/legacy wins
   per-report, not forced to match).

## 3. Endpoint (this service)

```
POST /reports/receipt
```
- `@UseGuards(InternalApiKeyGuard)` — same internal-only auth as the other two.
- `@Body() templateData: ReceiptReportTemplateData`
- `@Header('Content-Type', 'application/pdf')`
- Returns the raw PDF buffer, same shape as the other two report controllers.

`ReceiptReportsService` is the same one-line passthrough pattern.

## 4. `ReceiptReportTemplateData` contract

```ts
export interface ReceiptReportTemplateData {
  center: {
    name: string;
    address: string | null;
    landLine: string | null;
    logoBase64: string | null;
  };
  settings: {
    useImages: boolean;          // Center_Printable_Report_Settings.use_images (type 2) — only
                                  // meaningful when reportSize === 'A4' (§2 point 2)
    includeFooter: boolean;
    headerImageBase64: string | null;
    footerImageBase64: string | null;
    reportSize: 'A4' | 'A5';     // Center_PrintableReport_Sizes (report_type=2), center row else -1 default
  };
  receipt: {
    receiptNumber: number | null;       // Child_Payments/Child_Extra_Payment.center_receipt_number
    date: string;                       // "15/06/2026" (dd/MM/yyyy, matches the sample exactly)
    parentName: string | null;
    studentName: string;
    invoiceNumber: number | null;       // Child_Invoice.center_invoice_number; null for type 2
    description: string;                // invoice_title (type 1) or extra_payment_title (type 2)
    amount: string;                     // pre-formatted "1,254.00" (thousands separator)
    currencyCode: string;               // Currency.currency_name, e.g. "USD"
    amountInWords: string;              // "One thousand two hundred fifty-four USD only"
    paymentTypeTitle: string | null;    // Payment_Type.payment_type_title, e.g. "Cash"
    paymentNote: string | null;         // Child_Payments/Child_Extra_Payment.payment_note
  };
}
```

Notes:
- `settings.reportSize` is new relative to the other two contracts — neither Invoice nor Incident
  Report has a size toggle. `.hbs`/CSS branches on it (§5).
- No `feeLines`/discount/VAT the way Invoice has them — a receipt is a **single payment against a
  single installment**, one description + one amount, not a fee breakdown. Confirmed by the sample
  (`Description | Amount | Currency` table has exactly one row) and by legacy calling a completely
  separate SP (`getChildReceipt`) from the invoice's `getFeeTable`.
- `invoiceNumber` is `null` for `installmentType = 2` (extra payments aren't tied to an invoice) —
  the `.hbs` should skip that field/row entirely when null, same `{{#if}}` guard pattern as Invoice's
  optional `discount`.

## 5. `.hbs` template design (`src/templates/receipt-report/receipt-report.hbs`)

Layout reconstructed directly from the sample PDF's visual block order:

```hbs
<div class="center-header">
  {{#if center.logoBase64}}
  <img src="{{center.logoBase64}}" alt="Center Logo" onerror="this.style.display='none';" />
  {{/if}}
  <div class="center-info">
    <h2>{{center.name}}</h2>
    {{#if center.address}}<p>{{center.address}}</p>{{/if}}
    {{#if center.landLine}}<p>Phone: {{center.landLine}}</p>{{/if}}
  </div>
</div>

<div class="receipt-meta">
  <div><strong>Receipt No:</strong> {{receipt.receiptNumber}}</div>
  <div class="right"><strong>Date:</strong> {{receipt.date}}</div>
</div>

<div class="receipt-parties">
  <div><strong>Parent Name:</strong> {{receipt.parentName}}</div>
  {{#if receipt.invoiceNumber}}
  <div class="right"><strong>Invoice No:</strong> {{receipt.invoiceNumber}}</div>
  {{/if}}
  <div><strong>Student Name:</strong> {{receipt.studentName}}</div>
  <div class="right"><strong>Invoice:</strong> {{receipt.description}}</div>
</div>

<table class="fee-table">
  <thead>
    <tr><th>Description</th><th>Amount</th><th>Currency</th></tr>
  </thead>
  <tbody>
    <tr>
      <td>{{receipt.description}}</td>
      <td class="amount">{{receipt.amount}}</td>
      <td>{{receipt.currencyCode}}</td>
    </tr>
  </tbody>
</table>

<p class="amount-words"><strong>{{receipt.amountInWords}}</strong></p>

<div class="payment-by">
  <span><strong>Payment by:</strong> {{receipt.paymentTypeTitle}}</span>
  {{#if receipt.paymentNote}}<p>{{receipt.paymentNote}}</p>{{/if}}
</div>

<div class="signatures">
  <span>Parent Signature</span>
  <span>Accountant Signature</span>
</div>
```

- **Only two signature lines above** (`Parent Signature`, `Accountant Signature`), not the sample's
  four — the sample's extra `"Very Long Signature 1"` / `"Very Long Signature 2"` read as demo/test
  placeholder text (unusual, generic labels; no signature-label table or field exists anywhere in
  the schema search done for this doc), not a real, confirmed feature. Flagged in §6 — do not build
  a configurable signature-label list on the strength of this one sample.
- The sample's trailing `"Thank you! 123"` footer line is similarly treated as static template
  footer text (`"Thank you!"`) with `"123"` presumed stray demo input, not a data-driven field —
  flagged in §6 rather than modeled as a contract field.
- **`settings.reportSize === 'A5'`** switches to a compact CSS variant (smaller margins/font, no
  header/footer banner regardless of `useImages` — matches legacy always using `ReceiptReportSmall.
  rpt` for A5) via a body class (`{{#if (eq settings.reportSize "A5")}}compact{{/if}}`) rather than
  three separate template files — **one `.hbs` with a CSS branch**, not `receipt-report-a4.hbs` /
  `receipt-report-small.hbs` / `receipt-report-customized.hbs` the way legacy has three `.rpt`
  files. This is a deliberate modernization simplification (one source of truth for the markup,
  CSS handles the size difference) flagged for approval in §6, not assumed silently — legacy's three
  files might encode more than a CSS difference that isn't visible from a single A4 sample.
- Header/footer banner block only renders `{{#if settings.useImages}}` **and** implicitly only when
  `reportSize` is `A4` — the aggregation service should simply never populate
  `headerImageBase64`/`footerImageBase64` for an A5 receipt (§2 point 2), so the template doesn't
  need its own size check duplicated — one guard, not two.

## 6. Open items before implementation

- [ ] **Signature block**: sample shows 4 signature-line labels, two of which read as demo/test
      placeholder text. Confirm whether the receipt's signature lines are meant to be fixed (2, as
      proposed in §5) or a real configurable list — no backing table/field was found for the latter.
- [ ] **Footer text**: `"Thank you! 123"` — confirm whether `"Thank you!"` is genuinely static
      template text (as assumed) or center-configurable, and what `"123"` represents (if anything).
- [ ] **`installmentType = 2` (extra payment) sample not available** — the supplied sample is type
      1 (invoice installment) only. `description = extra_payment_title` and `invoiceNumber = null`
      for type 2 are inferred from `Center_Extra_Payments`'s schema, not confirmed visually.
- [ ] **`date` field source** — presumed `payment_date` (not `payment_value_date` or
      `modified_date`); not explicitly confirmed against a field name in the supplied C# snippet
      (same caveat as Invoice's `issueDate` open item).
- [ ] **Thousands-separator formatting**: worth revisiting `PaymentTuitionExportService.
      formatAmount()` (Invoice export, already shipped) for the same treatment, since `"328.00"`
      never actually exercised whether commas belong there too. Not changed as part of this doc —
      flagging only.
- [ ] **One `.hbs` + CSS branch vs. three template files for A4/A5/customized** (§5) — confirm this
      simplification is acceptable, or whether the legacy `.rpt` files differ in more than page
      size/banner presence.
- [ ] NurseryServices-Web: new `payment/payment-student-payment/export/` sub-module (ticket +
      download endpoints, mirroring the other two 1:1, with the `installmentType`-branching read
      described in §2) — not started, pending approval of this contract.
