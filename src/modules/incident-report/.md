# Incident Report Export — Design (proposal, not yet implemented)

> Mirrors `src/modules/evaluation-report` (see its `.md`). This file is a **design/contract doc
> only** — no code has been added to this service yet. Written for review/approval before
> implementation starts on either repo.

## 1. Overview

Renders the "Nurse Report" child incident PDF (legacy: `ExportIncidentReportData` /
`getChildIncidentInfo` SP, Crystal Reports `IncidentReport.rpt` /
`IncidentReportCustomized.rpt`). Modernized the same way evaluation-report was: **all data
aggregation and image-file resolution happens in NurseryServices-Web**; this service stays
"dumb" — it receives a finished JSON payload (images already base64-encoded) and turns it into a
PDF via Handlebars + Playwright. No DB access, no file-system access to icare photos, from this
service.

Reference legacy source: `new files/reports/daily reports/nurse/export/legacy endpoint.txt` +
`sql program.txt` + the sample output `Abdul Rahman_Incident_Report_on_08-26-2026.pdf`.

## 2. Data flow

1. NurseryServices-Web's incident-report export endpoint aggregates:
   - The incident report itself (reuses the existing `IncidentReportsService.findOwnedReport()` /
     `toIncidentReportItemDto()` TypeORM path — **no new stored procedure**; legacy's
     `getChildIncidentInfo` SP is just a single-row join across `Child_Incident_Report` → `Child`
     → `Parent` → `Center_Employee`, which the existing repo-based fetch already produces. An SP
     only earns its keep for list/pagination queries, not a single-row lookup.)
   - `Care_Center` row for the center's name/address/landline/logo (new — `IncidentReportsService`
     doesn't currently inject `CareCenter`).
   - `Center_Printable_Report_Settings` for `printable_report_type = 4` ("Incident Report" —
     already seeded in `PrintableReport_Types`), exactly like evaluation-report does for type 6.
     **Not dead weight** — legacy's `use_images` flag genuinely switches between `IncidentReport.rpt`
     (plain) and `IncidentReportCustomized.rpt` (with header/footer banner); the sample PDF just
     happens to come from a center with `use_images = false`, which is why it looks banner-less.
2. Images resolved to Base64 server-side, all nullable, all soft-fail-to-null (never throws):
   - Center logo: `Care_Center.center_logo` → `{PHOTO_FOLDER}/{centerId}/logo/{filename}` (new
     folder key, mirrors legacy `GeneralFunction.getCenterPhoto`'s `\{centerId}\logo\{imageURL}`
     path) → falls back to the shared default `{PHOTO_FOLDER}/icare/logo/blank_logo.png` if the
     center hasn't uploaded one / the file is missing.
   - Header/footer banners: same `Center_Printable_Report_Settings.header_image`/`footer_image` +
     `getImageAsBase64`-style read evaluation-report already uses, just against
     `printable_report_type = 4` instead of `6`.
3. NurseryServices-Web `POST`s the assembled `IncidentReportTemplateData` JSON to this service.
4. This service compiles `incident-report.hbs` with Handlebars, renders it in headless Chromium via
   Playwright, returns the PDF buffer.
5. NurseryServices-Web streams the PDF back to the client (same ticket/download-URL pattern as
   evaluation-report-export, `daily-reports/incident-reports` gets its own `export/` sub-module).

## 3. Endpoint (this service)

```
POST /reports/incident
```
- `@UseGuards(InternalApiKeyGuard)` — same internal-only auth as `/reports/evaluation`.
- `@Body() templateData: IncidentReportTemplateData`
- `@Header('Content-Type', 'application/pdf')`
- Returns the raw PDF buffer (`res.send(pdfBuffer)`), same shape as
  `ReportingController.createEvaluationReport`.

`IncidentReportsService` (this service) is a one-line passthrough, identical to
`EvaluationReportsService.createPdfFromData()`:
```ts
async createPdfFromData(templateData: IncidentReportTemplateData): Promise<Buffer> {
  return this.pdfService.generatePdfFromTemplate(templateData, 'incident-report');
}
```
(`PdfService.generatePdfFromTemplate` is currently hardcoded to the `evaluation-reports` template
path — it'll need a second template argument/branch to support both report types.)

## 4. `IncidentReportTemplateData` contract

```ts
export interface IncidentReportTemplateData {
  center: {
    name: string;
    address: string | null;
    landLine: string | null;
    logoBase64: string | null;       // real logo, or the icare/logo default — resolved server-side
  };
  settings: {
    useImages: boolean;              // Center_Printable_Report_Settings.use_images (type 4)
    includeFooter: boolean;          // useImages && include_footer
    headerImageBase64: string | null;
    footerImageBase64: string | null;
  };
  student: {
    name: string;
  };
  incident: {
    date: string;                   // "26/08/2026" (dd/mm/yyyy, matches legacy display format)
    time: string;                   // "7:15AM" (h:mmtt, matches legacy display format)
    title: string;
    description: string;
    actionsTaken: string;
    recommendedFollowUp: string | null;   // incidentMedicationsPrescribed
    reportedByName: string | null;
    parentContacted: boolean;
    parentContactTime: string | null;     // "7:15AM"; only meaningful when parentContacted
  };
}
```

Notes:
- `settings.*` mirrors evaluation-report's `ReportSettings` shape exactly (same field names) so the
  `.hbs`/`pdf.service.ts` conditional logic can be copy-adapted rather than reinvented.
- Deliberately **no** `legend`/`variants`/pagination/attendance fields — those are evaluation-report
  specific (term scores, age/attendance toggles). Incident report is a flat, single-record form.
- Date/time are pre-formatted strings (dd/mm/yyyy, h:mmtt), not ISO — matches the legacy exported
  document. The regular incident-reports API keeps returning ISO date / 24h `"HH:mm"` for its own
  consumers; the display reformatting happens only in the export aggregation step, same layering
  evaluation-report uses (`childInfo.dateFrom`/`dateTo` are pre-formatted with
  `.toLocaleDateString()` before reaching the template).

## 5. `.hbs` template design (`src/templates/incident-report/incident-report.hbs`)

Structure, following `evaluation-report.hbs`'s conventions (same header-image positioning CSS,
same nested-`{{#if}}` guards):

```hbs
{{#if settings.useImages}}
  {{#if settings.headerImageBase64}}
    <div class="first-page-header-container">
      <img src="{{settings.headerImageBase64}}" alt="Report Header" />
    </div>
    <div class="header-spacer"></div>
  {{/if}}
{{/if}}

<div class="center-header">
  <img
    src="{{center.logoBase64}}"
    alt="Center Logo"
    onerror="this.onerror=null;this.src='data:image/png;base64,<TEMPLATE-EMBEDDED-DEFAULT>';"
  />
  <div class="center-info">
    <h2>{{center.name}}</h2>
    <p>{{center.address}}</p>
    <p>Phone: {{center.landLine}}</p>
  </div>
</div>

<h1 style="text-align:center;">Incident Report</h1>

<table>
  <tr><th>Child Name:</th><td>{{student.name}}</td></tr>
  <tr><th>Date of Incident:</th><td>{{incident.date}}</td></tr>
  <tr><th>Time of Incident:</th><td>{{incident.time}}</td></tr>
  <tr><th>Reported by:</th><td>{{incident.reportedByName}}</td></tr>
  <tr><th>Incident Title:</th><td>{{incident.title}}</td></tr>
  <tr><th>Incident Description:</th><td>{{incident.description}}</td></tr>
  <tr>
    <th>Parent Contacted:</th>
    <td>
      {{#if incident.parentContacted}}Yes at {{incident.parentContactTime}}{{else}}No{{/if}}
    </td>
  </tr>
  <tr><th>Actions Taken:</th><td>{{incident.actionsTaken}}</td></tr>
  <tr><th>Recommended Follow up:</th><td>{{incident.recommendedFollowUp}}</td></tr>
</table>

<div class="signatures">
  <span>Manager Signature</span>
  <span>Nurse Signature</span>
  <span>Parent Signature</span>
</div>
```

- `center.logoBase64`'s `onerror` fallback is the **second, independent** default — a small image
  shipped with this service itself (e.g. `src/templates/incident-report/assets/default-logo.png`,
  inlined as base64 at build/startup, same way `registerHandlebarsHelpers` reads `node.hbs` as a
  partial today). Belt-and-suspenders: NurseryServices-Web already falls back to
  `icare/logo/blank_logo.png` on disk; this is what covers the case where that resolution somehow
  still produces nothing/garbage by the time it reaches this service.
- Footer (header/footer banner + page number) reuses `PdfService.buildFooterOptions()`'s existing
  logic as-is — it already keys off `settings.includeFooter`/`settings.footerImageBase64`, which
  this contract provides in the same shape.
- No `legend`/`node` partial needed — this is a flat table, not the evaluation report's recursive
  tree.
