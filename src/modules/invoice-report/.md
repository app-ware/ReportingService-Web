# Invoice Report Export — Design (proposal, not yet implemented)

> Mirrors `src/modules/incident-report` (see its `.md`) — same split, same conventions. This file is
> a **design/contract doc only** — no code has been added to this service yet. Written for
> review/approval before implementation starts on either repo.

## 1. Overview

Renders the tuition **Invoice** PDF (legacy: `ExportChildInvoiceReportData`, SPs
`getChildInvoiceInfo` / `getFeeTable` / `getReportVariants`, Crystal Reports `InvoiceReport.rpt` /
`InvoiceReportCustomized.rpt`). `PrintableReport_Types.printable_report_type_id = 1` ("Invoice",
already seeded). Same division of labor as evaluation-report/incident-report: **all data
aggregation, currency/amount-in-words formatting, and image-file resolution happens in
NurseryServices-Web**; this service stays "dumb" — JSON in, PDF out via Handlebars + Playwright.

Reference legacy source: `ExportChildInvoiceReportData()` (C# WCF, supplied directly), and a real
production sample PDF (`[Demo] mostafa gg55 Invoice.pdf`, supplied directly) used as the visual
ground truth below — no legacy SP bodies were available, so the field list is reconstructed from
the rendered sample cross-checked against `Child_Invoice`/`Child_Fee`/`Invoice_Discount`'s already-
known modern schema (`payment-tuition` module, NurseryServices-Web) and
`getChildInvoiceTotalValue`'s formula (`payment-tuition/doc/tuition-logic.md` §3b), not against the
legacy SPs directly.

## 2. Data flow

1. NurseryServices-Web's new `payment/payment-tuition/export` sub-module aggregates, for one
   `Child_Invoice` row (no new stored procedure — a single-record read, same reasoning as
   incident-report-export §2/skill 12 §2):
   - `Child_Invoice` (header: `center_invoice_number`, `invoice_date`, `invoice_title`,
     `academic_year`, `vat_amount`) — existing raw-query pattern `PaymentTuitionService` already
     uses via `ICARE_MSSQL_POOL` (this module has no injected TypeORM repos today; the export
     service either reuses that pattern or injects the `ChildInvoice`/`ChildFee`/`InvoiceDiscount`
     entities directly — implementer's call, not a contract concern).
   - `Child_Fee` rows for the invoice, in `is_additional` order (Tuition line first, then
     additional fees) — each becomes one fee-table row.
   - `Invoice_Discount` row for the invoice, if any (`TOP 1`, matches `getStudentTuitionForm`'s
     existing read) — rendered as a **negative** row in the same fee table (confirmed against the
     sample: label = `discount_description`, amount = `(discount_amount)` in parens).
   - Student/parent/class names via `vwChildClassParent` (same view every other export/tuition read
     in this codebase already uses) — `child_id` doubles as the sample's "Student ID" field.
   - `Academic_Years.title` for the academic-year label (`"2019-2020"` in the sample) — same join
     `iCareWebPanel_getCenterInvoicesData` already does for the list grid.
   - `Care_Center` row for center name/address/landline/logo **and** `center_currency` →
     `Currency.currency_name` (`"USD"` in the sample) — new reads for this export, same as
     incident-report-export newly injecting `CareCenter`.
   - `Center_Printable_Report_Settings` for `printable_report_type = 1` ("Invoice") — same
     use-images/header/footer toggle every other printable report type already supports (skill 12
     §6); not confirmed against a `use_images=true` sample, but treated as a real, wanted feature
     per that skill's default, not dropped just because the supplied sample has no banner.
2. **Computed in NurseryServices-Web, not the template** (skill 12 §7 — pre-format before it hits
   the payload):
   - `total = Σ(Child_Fee.fee_amount) + vat_amount − discount_amount` — exactly
     `getChildInvoiceTotalValue`'s formula (verified arithmetically against the sample: 200 tuition
     − 250 discount + 378 VAT = 328 total).
   - `totalInWords` — the total spelled out plus the currency name (`"Three hundred twenty-eight USD
     only"` in the sample). No existing number-to-words utility in NurseryServices-Web today — needs
     either a small vetted npm dependency (e.g. `to-words`) or an in-house helper; flagged as an open
     item (§6), not decided here.
   - All amounts pre-formatted to 2-decimal strings (`"200.00"`, `"(250.00)"`) — same reasoning as
     incident-report's pre-formatted dates/times, template does no math or formatting.
3. Images resolved to Base64 server-side, nullable, soft-fail-to-null — identical helper shape to
   incident-report-export (`getCenterLogoBase64` two-layer fallback, `getPrintableReportImageBase64`
   for header/footer banners against `printable_report_type = 1`).
4. NurseryServices-Web `POST`s the assembled `InvoiceReportTemplateData` JSON to this service.
5. This service compiles `invoice-report.hbs` with Handlebars, renders it in headless Chromium via
   Playwright (own `InvoiceReportPdfService`, copy-adapted from `IncidentReportPdfService` — this
   codebase's actual convention is one `PdfService` class per report module, not a shared
   parameterized one, despite what incident-report's own `.md` speculated before it was built).
6. NurseryServices-Web streams the PDF back via the same ticket/download-URL pattern (skill 12 §4),
   in a new `payment-tuition/export/` sub-module, filename `"{studentName} {invoiceTitle}
   Invoice.pdf"` (matches the legacy filename convention exactly, sanitized per skill 12 §9).

## 3. Endpoint (this service)

```
POST /reports/invoice
```
- `@UseGuards(InternalApiKeyGuard)` — same internal-only auth as `/reports/evaluation` and
  `/reports/incident`.
- `@Body() templateData: InvoiceReportTemplateData`
- `@Header('Content-Type', 'application/pdf')`
- Returns the raw PDF buffer (`res.send(pdfBuffer)`), same shape as the other two report
  controllers.

`InvoiceReportsService` (this service) is a one-line passthrough, identical to
`IncidentReportsService.createPdfFromData()`:
```ts
async createPdfFromData(templateData: InvoiceReportTemplateData): Promise<Buffer> {
  return this.pdfService.generatePdfFromTemplate(templateData);
}
```

## 4. `InvoiceReportTemplateData` contract

```ts
export interface InvoiceReportTemplateData {
  center: {
    name: string;
    address: string | null;
    landLine: string | null;
    logoBase64: string | null;   // real logo, or the icare/logo default — resolved server-side
  };
  settings: {
    useImages: boolean;          // Center_Printable_Report_Settings.use_images (type 1)
    includeFooter: boolean;      // useImages && include_footer
    headerImageBase64: string | null;
    footerImageBase64: string | null;
  };
  invoice: {
    invoiceNumber: number | null;       // Child_Invoice.center_invoice_number ("Invoice No")
    issueDate: string;                  // "06/20/2026" (MM/dd/yyyy, matches the sample exactly)
    academicYearTitle: string | null;   // Academic_Years.title ("2019-2020")
    studentId: number;                  // Child.child_id ("Student ID")
    studentName: string;
    parentName: string | null;
    className: string | null;
    feeLines: Array<{ title: string; amount: string }>;  // Child_Fee rows, pre-formatted "200.00"
    discount: { description: string; amount: string } | null;  // Invoice_Discount, "(250.00)"
    vatAmount: string;                  // pre-formatted "378.00"
    total: string;                      // pre-formatted "328.00"
    currencyCode: string;               // Currency.currency_name via Care_Center.center_currency
    totalInWords: string;               // "Three hundred twenty-eight USD only"
  };
}
```

Notes:
- `settings.*` mirrors incident-report's `ReportSettings` shape exactly (same field names), same
  reason as before — the `.hbs`/`pdf.service.ts` conditional logic is copy-adapted, not reinvented.
- Deliberately **no** `student`/`parent`/`class` nesting the way incident-report has a separate
  `student` object — the sample's info block interleaves invoice/student/parent/class fields in one
  visual block (Invoice No / Parent / Academic Year on one row, Student ID / Student / Class on the
  next), so keeping them flat under `invoice` matches the template's actual layout need better than
  forcing a nested shape that doesn't correspond to anything in the rendered document.
- `feeLines` is a flat array, not a dynamic-column pivot (unlike the Excel export's per-fee-title
  columns, skill 13 §6c) — a PDF fee table renders one row per fee regardless of how many distinct
  titles exist; no collision/column-naming concern here at all.
- `discount` is `null` when the invoice has no `Invoice_Discount` row — the `.hbs` template skips
  that table row entirely rather than rendering a blank/zero discount line (confirmed real invoices
  without a discount exist — it's optional per §3d of `tuition-logic.md`, "created only when
  `discount_id == -1`").
- Amount strings already carry sign/parens formatting (`"(250.00)"` for the discount) — the template
  does not add parens or a minus sign itself, avoiding a double-negative bug if the aggregation ever
  changes its convention.

## 5. `.hbs` template design (`src/templates/invoice-report/invoice-report.hbs`)

Structure, following `incident-report.hbs`'s conventions (same header-image positioning CSS, same
nested-`{{#if}}` guards) — layout reconstructed directly from the sample PDF's visual block order:

```hbs
{{#if settings.useImages}}
  {{#if settings.headerImageBase64}}
    <div class="first-page-header-container">
      <img src="{{settings.headerImageBase64}}" alt="Report Header" />
    </div>
    <div class="header-spacer"></div>
  {{/if}}
{{/if}}

<div class="info-block">
  <div><strong>Invoice No:</strong> {{invoice.invoiceNumber}}</div>
  <div><strong>Parent :</strong> {{invoice.parentName}}</div>
  <div><strong>Academic Year</strong> {{invoice.academicYearTitle}}</div>

  <div><strong>Student ID:</strong> {{invoice.studentId}}</div>
  <div><strong>Student :</strong> {{invoice.studentName}}</div>
  <div><strong>Class :</strong> {{invoice.className}}</div>

  <div class="issue-date"><strong>Issue Date:</strong> {{invoice.issueDate}}</div>
</div>

<table class="fee-table">
  <thead>
    <tr><th>Fee Description</th><th>Amount</th><th></th></tr>
  </thead>
  <tbody>
    {{#each invoice.feeLines}}
    <tr><td>{{this.title}}</td><td class="amount">{{this.amount}}</td><td></td></tr>
    {{/each}}
    {{#if invoice.discount}}
    <tr><td class="right"><strong>{{invoice.discount.description}}</strong></td>
        <td class="amount">{{invoice.discount.amount}}</td><td></td></tr>
    {{/if}}
    <tr><td class="right"><strong>VAT:</strong></td>
        <td class="amount">{{invoice.vatAmount}}</td><td></td></tr>
    <tr class="total-row"><td class="right"><strong>Total:</strong></td>
        <td class="amount"><strong>{{invoice.total}}</strong></td>
        <td>{{invoice.currencyCode}}</td></tr>
  </tbody>
</table>

<p class="amount-words"><strong>{{invoice.totalInWords}}</strong></p>
```

- No center-logo/name/address header block, no signatures block — **not present in the sample at
  all**. Unlike incident-report (whose `.hbs` was designed without a matching sample and included a
  center-header + signatures by convention), this template is built directly against a real
  rendered PDF that shows neither, so they're deliberately omitted rather than copy-pasted from the
  incident-report layout. If a `use_images=false` *and* logo-less sample is misleading the same way
  incident-report's `.md` flagged for itself (§6 of that doc), revisit once a `use_images=true`
  sample or the legacy `.rpt` file itself is available.
- `discount.description` renders as the row **label** (right-aligned, bold), not a separate column —
  matches the sample's `rtdhffffffffffffffff | (250.00)` row exactly (that string is literally
  `Invoice_Discount.discount_description`, a free-text field a center types in, same free-text
  nature as `Child_Fee.fee_title` elsewhere in this codebase).
- Footer (header/footer banner + page number) reuses the same `buildFooterOptions()`-style logic as
  the other two report PDF services, keyed off `settings.includeFooter`/`settings.footerImageBase64`.
- `center.logoBase64`'s `onerror` fallback: same second, independent default-asset pattern as
  incident-report's `.hbs` — **not used above** because the sample has no logo/header block at all;
  add it back only if a `use_images=true` sample surfaces one (see previous bullet).

## 6. Open items before implementation

- [ ] **Amount-in-words**: no existing number-to-words utility in NurseryServices-Web. Decide: small
      npm dependency (e.g. `to-words`) vs. an in-house helper. Either lives in the aggregation
      service (NurseryServices-Web), not here — this service only ever receives the already-formatted
      string.
- [ ] **`use_images=true` sample not available** — the supplied sample has no header/center-logo
      block at all, so §5's layout (no logo header, no signatures) may need revisiting once a
      customized-banner sample or the legacy `.rpt` files (`InvoiceReport.rpt` /
      `InvoiceReportCustomized.rpt`) are available to confirm the banner variant's exact layout.
- [ ] Confirm `issueDate`'s source column — legacy Crystal report showed `06/20/2026` next to
      "Issue Date"; this is presumed to be `Child_Invoice.invoice_date` (no other date field exists
      on the invoice header) but wasn't explicitly named in the supplied C# snippet.
- [ ] Legacy's `getReportVariants(@center_id)` recordset (`Report_Variants`) and its SP body were not
      supplied — nothing in the visible sample appears to depend on it (currency comes from
      `Care_Center.center_currency` → `Currency`, already covered above). Treated as **not required**
      for the modernized version unless a specific field from it is identified as missing once a
      broader set of sample invoices is reviewed.
- [ ] NurseryServices-Web: new `payment/payment-tuition/export/` sub-module (ticket + download
      endpoints, mirroring `daily-reports/incident-reports/export` 1:1) — not started, pending
      approval of this contract.
